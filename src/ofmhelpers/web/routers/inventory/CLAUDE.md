# web/routers/inventory

### inventory/
- `phones.py` — `/phones`: card per phone, its back drawn from the catalog (`GET /phones/drawing.svg`). The page never holds a secret: Show / Copy / Edit / recovery codes fetch one login from `GET /phones/logins/{id}/secret` (`no-store`, logs role + id, never values). Search (`data-search`) has no secrets. Everyone views, reveals, exports and edits their own phones only (another person's phone is a 404, admins included). `POST /{id}/logins`: an account already saved is linked, never copied; a different password is a 409. `/logins/{id}` edits it on every phone; `/{id}/logins/{login}/delete` unlinks (deleted when no phone has it). Delete removes a phone and the logins only it had. Duplicate 409, vault problem 500 with reason.
- **Assign phone (2026-11-13, owner: the VA added phones without Instagram and accounts on /accounts, so nothing got a Drive folder).** An /accounts row with no phone shows **Assign phone** -> `/phones?assign=<account_id>` (`PhoneQuery.assign`; not the reader's own tracked account = the normal page): pick mode, the shape of /drive's upload mode. `POST /phones/{device_id}/accounts` (`AssignAccount{account_id, replace}`, 201, `Phone.assign`): the account saved as a login with no password; another account of that service on the phone = 409 "<label> already has @old" unless `replace`, then each leaves by `Phone.remove_login` (off its last phone: untracked, folder to trash, password deleted; owner's choice 2026-11-13); a retired phone 409; unknown account or phone 404. The new account goes on BEFORE the old ones leave and an account already on the phone is no error (2026-11-13, review): a replace that fails half way leaves both on the phone, never none, and the same request again finishes it; a double click is one login. **Every tracked-service login put on a phone starts its owner's Drive sync at once** (`_make_drive_folder`: job row `drive_sync`, `run_job(drive_folders.sync, owner)`, only where the Drive sweep is enabled; a queue failure fails the row and the sweep makes the folder). Prod check 2026-11-13 (Logfire, the 6 `POST /phones/{device_id}/logins` of 14 days): the 3 with no `tracked_accounts` statement had no warning either, so they were logins of an untracked service; the 3 Instagram ones were tracked at once.
- `drive.py` — `/drive`: each card shows **Waiting: N** (one number, no split by kind) and **Uploaded to Drive today: N** (the clone / manual split is counted, `DriveCard.uploaded_today`, but not shown: the owner found the two extra numbers too much): the files in the account folder or its POSTED whose Drive `createdTime` is today (`OFM_GDRIVE_TIMEZONE`'s calendar day, `features/storage/folders.py` `_count_uploaded`, from the saved read: no Drive call, no table), Clone = the ones /clone's "Upload to Drive" made (`drive_uploads.drive_file_id`, `made_here`), Manual = the rest (put there by hand in Drive). A file moved to POSTED the same day still counts; one deleted the same day does not; /trials (TRIALS folder) and /clone-links (GOOD / TRIAL REELS) uploads are other folders, not counted. No page-level KPI line. Card per Instagram login; what waits (files directly in the account folder) as tiles, preview via `GET /drive/thumb/{id}` (server fetches Drive's `thumbnailLink` with the bot's token; 404 = icon instead); extra POSTED folders flagged; other subfolders are not shown. `POST /drive/sync` -> `SyncReport` (anyone's Sync, an admin's too, sweeps and reports only their own phones; the background loop does everyone's) (502 with reason when Drive refuses). Not set up / not shared -> notice naming the bot's email. Folders in the root no login owns are listed under a fold (cleanup); the reader's VAs' own folders are listed above it under "VAs", by name (`DriveBoard.va_folders`, web/CLAUDE.md "Backlog 2026-11-15"), never in that fold. Everyone signed in. `drive.js`.
- `handmade.py` — `/handmade`: a VA's handmade reels into their own Drive folder (web/CLAUDE.md "Backlog 2026-11-15"); cards built here like `registry.task_card` (the registry imports this router), `_handmade_card.html`, `handmade.js` adds "In Drive" to a card that finishes live.
- Data: `logins` store "" plain (secrets are `EncryptedText`) so lists know `has_password` without decrypting.

- **History and backup (2026-11-14, owner: "every action will have revision ... enforced on db level ... go back to any state").** Table `phone_revisions` (alembic b7c8d9e0f1a3): one row per transaction that touched a person's `devices` / `logins` / `device_logins`, holding all their rows of the three tables after it (`snapshot` JSONB; secrets are the columns' Fernet text). Written by the trigger `phone_revision()` on those tables, so no code path (nine repository methods, cascades, the Drive sweep, psql) can skip it; `phone_revisions_guard()` refuses UPDATE (but the same transaction's upsert), DELETE and TRUNCATE. Unique `(user_id, txid, created_at)`: transaction ids start over in a restored database. The SQL argument is `whose`, not `owner`: `devices` has an `owner` column. `features/phones/revisions.py` `Revisions(scope)`: `POST /phones/revisions/{id}/restoration` (201): one transaction in `db/phone_revisions/repository.py` -- rows added since deleted, labels and usernames parked (`~<id>`: a swap would trip the unique constraints), the revision's rows upserted by primary key through `jsonb_populate_recordset` (a row that still exists keeps its Drive rows; no decrypting). A column added to a phone table later must have a default, or an older revision no longer restores. The restore is recorded as a new revision. Drive is never touched: accounts that came back are tracked again (`track_login`, revive), their folders made by the next sync; ones that left keep their folder. Tests wipe under `session_replication_role = replica` (root and e2e conftest), which skips the triggers.
- **Backup file** (`features/phones/backup.py`, sweep `phones backup` every `OFM_PHONES_BACKUP_SWEEP_S` 300 s, only with a vault key): the whole History of every owner as one JSON, encrypted whole with `OFM_VAULT_KEY`, `<uploads>/backups/phones/phones-YYYY-MM-DD.json.enc`; written only when the newest revision id differs from `last-revision` next to it; newest `OFM_PHONES_BACKUP_KEEP` 30 files kept. `python -m ofmhelpers.features.phones.backup load <file>` puts back the revisions the table lacks (same person, moment and change = already there), changes no phone.
