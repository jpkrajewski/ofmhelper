# web/routers/downloads

### downloads/
- The work is `features/downloads/` (`service.py` `queue_downloads`, `media.py` + `send`, `videos.py`, `images.py`, `clean.py`) and `features/reels/page.py` (2026-11-11); the routers keep `_run_downloads` / `_run_clean` as names only (jobs queued before name them by the router's path).
- **A video is kept a while, then only its poster (2026-11-11, owner; prod disk 84-93%, nothing ever deleted `downloads/`, and `./uploads` + `./downloads` are two mounts, so the asset store's "hard link" of each download is a second copy).** Table `downloads` (alembic f4b5c6d7e8a1; `db/repositories/downloads.py`, `db/stores/downloads.py`, `schemas/downloads.py` `Download`): one row per downloaded file -- `user_id`, `job_id` + `position` (the `{i}` of `/files/{job}/{i}`), `url`, `file_path`, `asset_path` (its copy in the asset store; NULL on rows the revision made from old jobs, filled by the sweep by content hash), `stored`, `created_at`, `last_used_at`, `removed_at`. Written by `features/downloads/service.py` `fetch` when a download job finishes (the job row stays the run's record).
  - **Same link, no second download** (`features/downloads/again.py` `sort_out`, called by `queue_downloads`): a link repeated in a paste counts once; a link the person downloaded before (their own rows only) makes no job -- `last_used_at` = now, its card unhidden if hidden; only new links make a job. `POST /download-media/run` answers `DownloadsQueued`: `job_id` / `job_ids` (the new job; none when every link was there) + `again` (jobs already holding a link); `download.js` redraws those cards at the first place from `/download-assets/gallery`. The gallery orders by the newest `last_used_at` of the job's rows, else `created_at` (`JobRepository.page_by_use`, uncached; `Gallery(by_use=True)`). Not covered: a link pasted again while its first download still runs (no rows yet) downloads twice.
  - **Sweep `downloads cleanup`** (`features/downloads/cleanup.py`, hourly on `previews`, `OFM_DOWNLOADS_KEEP_UNUSED_S` 86400 / `KEEP_CLONED_S` 1209600 / `KEEP_MAX_S` 2592000 / `SWEEP_S` 3600; **production only unless `OFM_DOWNLOADS_SWEEP`**, dev has prod's rows next to the developer's own files): looks at stored rows idle (`last_used_at`) for a day, 50 at a time. `unused`: no job's params name its asset copy (matched by the `<sha256>` in the copy's name, `JobRepository.naming_each`), a day after it was last asked for; `cloned`: 14 days after the newest job naming it started (that moves `last_used_at`); `max`: 30 days after `created_at`. Nothing asked for or used within a day goes (a video fetched again stays a day). Never: one a running job names, one whose own job is running, one whose poster cannot be made (an image: its small preview). Goes: the `downloads/<hex>/` file (+ empty folder), the 720p preview, the asset copy unless another stored download is the same file, a job's result is it, or (the `max` rule) a clone used it within 14 days. Stays: row (`stored` false), job, poster. A file already gone is only marked. One log line a round. `python -m ofmhelpers.features.downloads.cleanup` = the dry count (`dry_count`), writes nothing; without the file (dev) a use is read from the file's name: an estimate.
  - **Fetch again = the same job run again** (`service.fetch`: a link whose files are on disk is skipped, the rest fetched, rows updated in place, stale previews dropped; a link that can no longer be fetched keeps its entry, card and poster). Started by `POST /download-media/{job_id}/replays` (202 `{job_id}`; own jobs only; `Restart.replay`: `reopen_settled` is one UPDATE, so of two clicks one queues; no restart counter), by the link pasted again, and by a clone's Recreate. A removed file keeps its place in the job's result (`db/stores/jobs.py` `_visible`), its card shows `<img class="result-video">` (the poster) and one Download (`.download-again`), no Clone control until it is back; `/files/{job}/{i}` and `/preview` answer **410** `Removed to save space: download it again`, `/poster` the kept poster. `AssetCard.removed`.
  - **Recreate** (`/refs/missing` `restorable: [{path, job_id, index}]`: the asker's own removed downloads among the missing, matched by digest): `file-picker.js` `restore` keeps such a file in the list as "Downloading again…", posts the replay, polls the job, then asks `GET /download-media/{job_id}/files/{index}/stored` for the path it has NOW (other bytes hash differently) -- every page's Recreate, not only /clone's; /clone's Start waits (`FilePicker.restoring()`).
- **"Download from Drive sheet" (2026-11-12, owner; `features/downloads/sheet.py`).** People add links from their phones to the Google Sheet `OFM_DOWNLOADS_SHEET_NAME` (`content_links`) in the owner's Drive root (`features/drive/folders.py` `find_root`: the stored root, else found by name; nothing made), one column per day, the date in row 1, links under it (prod's shape that day: one tab, A1..P1 = 12/11..27/11 as date cells, Instagram reel links with share-tracking queries below). The toolbar button (left of Show hidden, `_gallery_hidden.html` with `sheet_cooldown_s`; `download.js`) -> `POST /download-media/sheet-downloads` -> `SheetQueued`: reads the sheet now (`gdrive` `find_file` + `sheet`), takes today's column (`OFM_GDRIVE_TIMEZONE`'s day; every tab scanned, the column found by its date, never by position; a cell that is not a link is counted in `skipped`), drops links the person has `downloads` rows for and links an earlier click queued (Redis set `downloads:sheet:<user>:<day>`, `OFM_DOWNLOADS_SHEET_CLAIM_S` 3 days: a link whose job still runs has no row yet), and queues the rest as ONE ordinary `download_media` job (`service.Links.queue`, params `urls` + `sheet_date`), so cards, replays, retention and recovery are the Download tool's. Nothing new = no job, "No new links for 12/11". Unlike a paste, links downloaded before are left alone (no card moved, no removed video fetched again). The button rests `OFM_DOWNLOADS_SHEET_COOLDOWN_S` (60) after every click, per person (Redis `SET NX EX`; 429 `Wait N s`; Redis down: allowed), also across a reload. A VA's click reads the employer's sheet. Refusals: no Drive 400, no sheet / no column for today 404, Drive failed 502; a refused click does not rest the button (`Clicker.wake`), only one that read the day's links does. `Clicker` (one person's cooldown + claims in Redis): a claim cut off by Redis part-way unmarks what it marked (503 `Could not start the download. Try again.`). The sheet's export is refused above `OFM_GDRIVE_SHEET_MAX_BYTES` (2 MiB) before it is parsed. A VA and the employer each have their own history: the VA's click after the employer's makes the VA's own job and cards, without fetching again (`service.fetch` reuses files on the server). Dev reads the live sheet in read-live mode (`OFM_DRIVE_READ_LIVE`), else one in "DEV - ALL ACCOUNTS". Not done: a link that failed is not tried again by the button (its card's Recreate does); the same reel shared with another tracking value counts as another link.
- `index.py` picker: Download (any link) + Clean image metadata. Every file of a download is its own card (`TaskCard.per_file`, user decision 2026-11-03; a run finishing on the page always drew them so), Clone / Clone long on a card sends that card's video (`/download-media/send` `index`), Hide hides the whole download (`jobs.hidden_at` is per job), the links that failed show once, on the first card. `media.py` (`/download-media`, task `download_media`): one tool, `downloaders.media` picks yt-dlp/gallery-dl per link (2026-10-21: nobody chooses videos vs images). `videos.py`/`images.py` keep only their old jobs' routes; Recreate maps those runs onto Download (`data-tasks`). `clean_image.py`: the shared file picker without Reuse (`reuse=false`, only new files; a second pick adds, it does not replace as a plain file input did; `required=true`: an empty list stops the form), emptied once a batch is queued (`generation:queued`).
- `reels.py` — `/reels`: watched Instagram profiles in groups, ranked by `schemas.Leaderboard`; one flat feed filtered by `?group=`/`?rank=` (`VIEW_TIERS`: 50k/100k/200k/500k/1M+), paged 60. Scans keep reels within `max_age_days`, >= `min_views`, <= `max_duration_s` (15 s, Wan 3.0's cap; the feed hides longer stored reels too). `POST /reels/watch` adds/moves, queues scans (never in-request). Picks in `sessionStorage`; `POST /reels/clone` saves picks to the store and redirects to `/clone?video=`; `POST /reels/download` returns mp4/zip.

- `viral.py` — `/viral` (More, first; 2026-10-31, replaces the /reels watch-list chore for "what went viral on @x"): one profile field (handle or link, `ProfileHandle`) -> `POST /viral/run` -> job `viral_reels` on the worker (`run_viral`: `ofmhelpers.features.viral.find_viral`, then `merge_params` `scanned` + `cost_usd`; result = `ViralFile` entries: file + code/url/plays/likes/comments/posted_at/seconds). Page shows `?job=` (own jobs only) else the newest search: running = a spinner `viral.js` polls (`/viral/jobs/{id}/status`, hidden tab waits, failed polls retried) then reloads; failed = one notice with the short reason (`schemas/errors.py`: Profile not found, No reels, No Apify credit, Wrong API key); done = "@x · top N of M reels · $cost" + Download all (`GET /viral/zip/{job}`, stored zip `01-<code>.mp4`... most played first) and one card per reel (preview/poster via the job file routes, "1.2M plays · 40k likes · 17 s · date", Download, open on Instagram). Header: "200 newest reels a search · up to $0.52". Earlier searches = buttons under the form (newest 20). See viral/CLAUDE.md, apify/CLAUDE.md.
