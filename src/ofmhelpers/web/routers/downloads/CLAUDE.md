# web/routers/downloads

### downloads/
- **One `DownloadService` (`features/downloads/service.py`, owner 2026-11-22).** Built once per request by `web/dependencies.py` `Downloads` (`DownloadService.compose(actor, owner_id, assets_root, EmployerStorage)`); its parts: `again` (`Again`: sort out a paste, replay, stored file), `media` / `videos` / `images` (`LinkDownloads`: start a paste, queue links as one job), `sheet` (`SheetDownloads`: cooldown, claims, today's links through `storage.sheet`), `storage`. A route calls one method of a part; the RQ entries `media|videos|images.run_downloads` and `fetch.py` are the job side.
- The routers keep `_run_downloads` / `_run_clean` as names only (jobs queued before name them by the router's path).
- **A video is kept a while, then only its poster (2026-11-11, owner; prod disk 84-93%, nothing ever deleted `downloads/`, and `./uploads` + `./downloads` are two mounts, so the asset store's "hard link" of each download is a second copy).** Table `downloads` (alembic f4b5c6d7e8a1): one row per downloaded file; `asset_path` is its copy in the asset store (NULL on rows the revision made from old jobs, filled by the sweep by content hash). Written by `features/downloads/fetch.py` `fetch` when a download job finishes (the job row stays the run's record).
  - **Same link, no second download** (`features/downloads/again.py` `Again.sort_out`, called by `links.py` `LinkDownloads.start`): a link repeated in a paste counts once; a link the person downloaded before (their own rows only) makes no job -- `last_used_at` = now, its card unhidden if hidden. `POST /download-media/run` answers `DownloadsQueued` (`job_id` / `job_ids`, none when every link was there, + `again`: jobs already holding a link). The gallery orders by the newest `last_used_at` of the job's rows, else `created_at` (`JobRepository.page_by_use`, uncached). A link one of the person's download jobs is still fetching counts too (2026-11-20, Zalando #231 secondary key: `jobs.store.running_with_links`, a JSONB `?|` on `params.urls` of their running download jobs): no second job, that job in `again`. The same click sent twice is the Idempotency-Key layer's (`web/idempotency.py`).
  - **Sweep `downloads cleanup`** (`features/downloads/cleanup.py`, hourly on `previews`, settings `OFM_DOWNLOADS_KEEP_*` / `SWEEP_S`; **production only unless `OFM_DOWNLOADS_SWEEP`**, dev has prod's rows next to the developer's own files): looks at stored rows idle (`last_used_at`) for a day, 50 at a time. `unused`: no job's params name its asset copy (matched by the `<sha256>` in the copy's name, `JobRepository.naming_each`), a day after it was last asked for; `cloned`: 14 days after the newest job naming it started (that moves `last_used_at`); `max`: 30 days after `created_at`. Nothing asked for or used within a day goes (a video fetched again stays a day). Never: one a running job names, one whose own job is running, one whose poster cannot be made (an image: its small preview). Goes: the `downloads/<hex>/` file (+ empty folder), the 720p preview, the asset copy unless another stored download is the same file, a job's result is it, or (the `max` rule) a clone used it within 14 days. Stays: row (`stored` false), job, poster. A file already gone is only marked. `python -m ofmhelpers.features.downloads.cleanup` = the dry count (`dry_count`), writes nothing; without the file (dev) a use is read from the file's name: an estimate.
  - **Fetch again = the same job run again** (`fetch.fetch`: a link whose files are on disk is skipped, the rest fetched, rows updated in place, stale previews dropped; a link that can no longer be fetched keeps its entry, card and poster, and since 2026-11-12 the downloader's words as `DownloadResult.again_error`: the card says why under the poster (`AssetCard.removed_reason`, `features/jobs/schema.py` `error_reason`: "Post deleted or profile banned" for yt-dlp's "empty media response" / "Video unavailable", "Needs login" for its login redirect; full text in `title`; the status payload carries both, generation.js `buildRemovedReason`), `GET .../stored` refuses with that reason and a clone's Recreate shows it ("<name> could not be downloaded again: ...") instead of "is not on this server: pick it again"; a fetch that works clears it. Prod 2026-11-12, job 65a6bb46 (old `download_videos`, reel of a banned profile): five clicks on Download, each ending in the bare poster, the reason only in the log. yt-dlp cannot tell a deleted post from a banned or private profile: one label names them). Started by `POST /download-media/{job_id}/replays` (202 `{job_id}`; own jobs only; `Restart.replay`: `reopen_settled` is one UPDATE, so of two clicks one queues; no restart counter), by the link pasted again, and by a clone's Recreate. A removed file keeps its place in the job's result (`db/jobs/store.py` `_visible`), its card shows `<img class="result-video">` (the poster) and one Download (`.download-again`), no Clone control until it is back; `/files/{job}/{i}` and `/preview` answer **410** `Removed to save space: download it again`, `/poster` the kept poster. `AssetCard.removed`.
  - **Recreate** (`/refs/missing` `restorable: [{path, job_id, index}]`: the asker's own removed downloads among the missing, matched by digest): `file-picker.js` `restore` keeps such a file in the list as "Downloading again…", posts the replay, polls the job, then asks `GET /download-media/{job_id}/files/{index}/stored` for the path it has NOW (other bytes hash differently) -- every page's Recreate, not only /clone's; /clone's Start waits (`FilePicker.restoring()`).
- **"Download from Drive sheet" (2026-11-12, owner; `features/downloads/sheet.py`).** People add links from their phones to the Google Sheet `OFM_DOWNLOADS_SHEET_NAME` (`content_links`) in the owner's Drive root (`features/storage/sheet.py` `StorageServiceSheet.get_by_name(name).column(day)`: root from `StorageServiceFolders.find_root`, the stored root, else found by name; nothing made; the employer's storage from `web/dependencies.py` `Downloads`), one column per day, the date in row 1, links under it (Instagram reel links with share-tracking queries). The toolbar button -> `POST /download-media/sheet-downloads` -> `SheetQueued`: reads the sheet now, takes today's column (`OFM_GDRIVE_TIMEZONE`'s day; every tab scanned, the column found by its date, never by position; a cell that is not a link is counted in `skipped`), drops links the person has `downloads` rows for and links an earlier click queued (Redis set `downloads:sheet:<user>:<day>`, `OFM_DOWNLOADS_SHEET_CLAIM_S` 3 days: a link whose job still runs has no row yet), and queues the rest as ONE ordinary `download_media` job (`LinkDownloads.queue`, params `urls` + `sheet_date`), so cards, replays, retention and recovery are the Download tool's. Nothing new = no job, "No new links for 12/11". Unlike a paste, links downloaded before are left alone (no card moved, no removed video fetched again). The button rests `OFM_DOWNLOADS_SHEET_COOLDOWN_S` (60) after every click, per person (Redis `SET NX EX`; 429 `Wait N s`; Redis down: allowed), also across a reload. A VA's click reads the employer's sheet. Refusals: no Drive 400, no sheet / no column for today 404, Drive failed 502; a refused click does not rest the button (`Clicker.wake`), only one that read the day's links does. `Clicker` (one person's cooldown + claims in Redis): a claim cut off by Redis part-way unmarks what it marked (503 `Could not start the download. Try again.`). The sheet's export is refused above `OFM_GDRIVE_SHEET_MAX_BYTES` (2 MiB) before it is parsed. A VA and the employer each have their own history: the VA's click after the employer's makes the VA's own job and cards, without fetching again (`fetch.fetch` reuses files on the server). Dev reads the live sheet in read-live mode (`OFM_DRIVE_READ_LIVE`), else one in "DEV - ALL ACCOUNTS". Not done: a link that failed is not tried again by the button (its card's Recreate does); the same reel shared with another tracking value counts as another link.
- `index.py` picker: Download (any link) + Clean image metadata. Every file of a download is its own card (`TaskCard.per_file`, user decision 2026-11-03), Clone / Clone long on a card sends that card's video (`/download-media/send` `index`), Hide hides the whole download (`jobs.hidden_at` is per job). `media.py` (task `download_media`): one tool, `downloaders.media` picks yt-dlp/gallery-dl per link (nobody chooses videos vs images). `videos.py`/`images.py` keep only their old jobs' routes; Recreate maps those runs onto Download (`data-tasks`). `clean_image.py`: the shared file picker without Reuse (`reuse=false`, only new files; `required=true`: an empty list stops the form).
- `reels.py` — `/reels`: watched Instagram profiles ranked by `db/watched_profiles/schema.py` `Leaderboard`. Scans keep reels within `max_age_days`, >= `min_views`, <= `max_duration_s` (15 s, Wan 3.0's cap; the feed hides longer stored reels too). `POST /reels/watch` queues scans, never in-request.
- `viral.py` — `/viral`: one profile field -> `POST /viral/run` -> job `viral_reels` (`run_viral`: `features.viral.find_viral`, then `merge_params` `scanned` + `cost_usd`; result = `ViralFile` entries). Page shows `?job=` (own jobs only) else the newest search. See viral/CLAUDE.md, apify/CLAUDE.md.
