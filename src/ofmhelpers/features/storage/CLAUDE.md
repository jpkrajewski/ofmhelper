# storage

/storage (More menu, owners): what each account folder holds in the owner's Google Drive, and moving its TRIALS, SPOOFED or THREADS content to the bin, for one folder or for all of them (owner 2026-11-22).

- **Soft only.** A move puts every item directly inside that part folder in Google Drive's Bin (`trash_file`; a thread set folder goes whole, its pictures with it). The part folders themselves stay, so the ids other pages keep stay valid. Nothing is ever deleted for good: the Drive interface has no delete, and `tests/unit/storage/test_never_deletes.py` fails on any `emptyTrash`, `permanently_delete` or `.delete(` call in a storage client. The bin still counts against the owner's quota until they empty it; Google empties it by itself after 30 days (https://support.google.com/drive/answer/2375102).
- **Scan** (`storage_scan`, `jobs.run_scan`): the owner's account folders that are listed in their root now (stored ids alone can be stale, and one unknown id 404s a batched listing), walked breadth-first with `children_of`, summing `DriveFile.size`; TRIALS, SPOOFED and THREADS one level below the account folder are counted apart. The result is the job row's `result` (`StorageUsage`, with the core `DriveStorage` quota as is). The page GET starts one when the newest is older than `OFM_STORAGE_SCAN_STALE_S` (600) or older than the last move; a running one is never started twice (Redis lock + running-row check).
- **Move** (`storage_bin`, `jobs.run_bin`, params `BinMove`): one per owner at a time (`ConflictError` 409 "Already moving files to the bin"); a folder id not among the owner's account folders is a 404. A rerun lists only what is not in the bin yet and moves the rest, so both tasks are in `background/registry.py` `RESTARTS`. Result `Moved`: items and bytes moved.
- A move during an upload into the same part can put a file uploaded a moment before in the bin too; it stays restorable there.
- Distribution: a post whose THREADS picture went to the bin fails like any download and stops after `OFM_DISTRIBUTION_MAX_ATTEMPTS` (3). Not made final on purpose: `FolderGoneError` is also Drive's ambiguous 404 (integrations/storage/gdrive/CLAUDE.md).
- The page GET with the queue down shows the last scan (the scan row it made is restarted by recovery), never a 500.

## One client injected, one StorageService (owner 2026-11-22: "bullshit service layer that is importing functions from other modules in other classes. no dependency injection")
- `client.py` is the factory and the only importer of `integrations.storage.gdrive` (a provider is chosen here, nowhere else): `access(user_id, interactive)` -> `StorageAccess` (models.py: the one raw client = the person's Google Drive, else the agency's Drive bot; `bot` = `BotRoot` when it is the bot; `read_live` = `OFM_DRIVE_READ_LIVE` outside production, `GDriveSettings.live_read`), `storage_of(user_id, interactive)` = `StorageService.compose(access(...))`, `saved_storage(user_id)` = the same with no client, for a job that reads only saved state (the trials POSTED read runs on the default worker through `saved_storage`, so no token is read; the copy cleanup on previews reads no storage), `storage_owner` (a VA's employer).
- `service.py` `StorageService.compose(access)` builds every sub-service once and hands each the same client and the sub-services it needs: `folders`, `va_folders`, `review`, `uploads`, `space`, `page`, `bin`, `sheet` (`StorageServiceSheet.get_by_name(name)` -> `models.Sheet`, whose `column(day)` is that day's links).
- **A feature takes storage as a part of its own composite, never as a function argument** (owner 2026-11-22: "one download service that also aggregates this and takes storage as a composite part"): `features/downloads/service.py` `DownloadService.compose(actor, owner_id, assets_root, storage)` is the shape. Drive work stays in a storage sub-service; nothing outside storage imports the raw client (`StorageClient`, `ReviewPlace`, `DriveSheet`, the wrappers). `tests/unit/architecture/test_storage_di.py` checks both; its `NOT_MOVED_YET` lists the files still to move (trials, threads, distribution, the upload picker, clone_links, accounts removal) and only shrinks. In read-live mode it wraps the client in `ReadOnlyDrive` for all but `review`, which keeps the raw one and scopes it to the DEV root (`ScopedDrive`) as before; uploads, review and space get no client when it is the bot (they need a quota). A sub-service never builds a client or another sub-service and never calls a sibling module's function.
- Composition roots: `web/dependencies.py` (`Storage`: the signed-in scope's, interactive client; `EmployerStorage`: the VA's employer's, only for the Drive sheet) and the RQ entries (`jobs.py`: `sync`, `upload_files`, `run_scan`, `run_bin`; the trials, threads, distribution and clone_links tasks), each `storage_of(user_id, interactive=False)` once. `/drive/sync` calls `jobs.sync(owner=scope)`, the sweep's function. `features/drive/{folders,uploads}.py` re-import the entries for jobs queued under the old paths.
- Other code imports only `service`, `jobs`, `client` (composition roots), `constants`, `schema`, `models`, `posting`: `tests/unit/architecture/test_storage_di.py` (no baseline) also fails on a provider import outside the factory and on a `StorageService*(` built outside `compose`.
- A factory client is a `PerThreadDrive` (`integrations/storage/wrappers.py`): it opens the provider on its first call, one per thread, so the thread pools (`_tally`, `_list_each`, the root check) share the one client, and a refused sign-in raises at the first call inside the caller's try, never while a dependency builds it.
- Trials tasks still take the `refresh_token` kwarg of jobs queued before 2026-11-22 and ignore it; new jobs carry no token.

## Dropbox and deleting
- Dropbox's `trash_file` calls `files_delete_v2`, which Dropbox keeps as a Deleted file, restorable for 30 days on Basic (https://help.dropbox.com/delete-restore/restore-deleted-files). That is the one exempt call: `tests/unit/storage/test_never_deletes.py` fails on every other `files_delete*` call and on `.delete(`.
- `/drive/folders/{id}` (`db/drive_folders/schema.py` `folder_url`) is the app's own link and is what a threads job result keeps (`features/threads/tasks.py` `folder_url`): it only has to open inside the app, which redirects to the provider's page. It is not a provider web url.
- Switching provider with stored folder rows loses nothing: `db/drive_folders/store.py` `account_folders()` returns only rows whose root is the owner's current `drive_root_id`, every switch clears it and the sync sets the new root before reading rows (`tests/integration/web/test_storage_provider_switch.py`).
