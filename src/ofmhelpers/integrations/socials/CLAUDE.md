# socials

Tracked social accounts, platform-agnostic. Each platform turns a handle into `AccountStats`; `features/accounts/tracker.py` scans on a schedule (and on /accounts Sync), `/accounts` (`web/routers/tracking/accounts.py`) shows them.

## Sources: one caller, every way of reading (2026-11-07, owner: "apify first, then proxy + our client; cookies flaky, can get you banned")
- `sources.py` — `AccountSource.scan(targets) -> Answers`, everything keyed by `ScanTarget.key` = the tracked account's id, never the handle (two users may track one handle: one's login must never fill the other's row; a logged-out read of a shared handle is made once and given to both). `scan_through(sources, targets, on_read)`: each source gets only what the ones before left unread; `on_read(key, stats)` saves a read the moment its source answered (review 2026-11-07: a job killed after Apify paid would have re-paid at the claim's expiry); a source that raises is logged and skipped (its batch goes on whole); `AccountStats.source` / `AccountMetrics.source` = who answered. A refusal the platform itself gave (`reached`) outlives a later "never got there". Tracker: unread -> the reached refusal, else `tracker.UNREACHED` ("No source could read it now -- retried at the next scan"), saved as its error: numbers kept, claim released, failure backoff (a standing claim retried, and paid Apify, every `claim_ttl_s`, and kept Sync greyed out that long).
- Order = `OFM_ACCOUNTS_SOURCES` (default `api,proxy,login`): `Platform.sources(start)` builds them; `api` = `Platform.api_source()` (None: the platform has none), `proxy` = `client_source.ProxySource` (our `fetch` logged out, proxies in turn, jitter, dead proxy dropped, every try rate-limited or direct connection down ends the source for the rest of the batch), `login` = `LoginSource` (same, with the owner's cookies; skips accounts whose owner has none). Last resort only.
- `platforms/instagram_apify.py` — `ApifyInstagramSource`: keys `APIFY_API_KEYS` (`settings.viral.api_keys`) by credit left, most first (`apify.by_credit`); a key takes as many accounts as `credit - 2 runs` covers at `OFM_ACCOUNTS_APIFY_USD_PER_ITEM` (0.0026) x (1 profile + `OFM_ACCOUNTS_APIFY_EST_REELS` 15). Per key: `apify~instagram-profile-scraper` (`usernames`, followers/avatar/private/verified; a renamed account matched by `inputUrl`) then `apify~instagram-reel-scraper` for the public ones (`onlyPostsNewerThan: "7 days"` = `OFM_ACCOUNTS_APIFY_DAYS`, `resultsLimit` `track_max_reels`+1, add-ons off; `videoPlayCount`). Stats: `complete=False`, `since` = now - 7 d, and `reach` = `since` whatever older post came along (a pinned one says nothing about the posts between); reels deduped by shortCode; older kept posts keep their last views. Reels asked by each profile's CURRENT username (a renamed account's old handle may be someone else's). Reel run failed / out of credit / not SUCCEEDED (cut short): none of its reels kept (half a read would save wrong views), its PUBLIC accounts go to the next key, then the next source -- the private ones and the paid profiles are kept; profile run failed: its whole group goes on; an account the profile run did not return while it SUCCEEDED (not found) goes straight to the next source, never paid for on another key. One batch spends at a time (Redis lock `lock:accounts-apify`, held for up to every key's two runs; not had in time -> the batch goes to the next source; Redis down -> goes ahead): parallel batch jobs each sizing their share from the same credit figure spent it several times over. Cost at prod 2026-11-07 (10 accounts, ~13 reels / 7 d): ~$0.36 a sync; logged per key (`apify key ...: N of M accounts read, R reels, $X`).
- New platform (Threads, Facebook, ...): its `Platform` subclass (`fetch` = its own client, raising only socials errors) + `api_source()` returning its Apify actor source; the tracker, chain and page do not change.

- `schemas/socials.py` (re-exported by `models.py`; moved down 2026-11-11: `db/stores` and `schemas/accounts.py` use them) — `PlatformNames` (a platform's `key`, `label`, `handle()`, `profile_url()`: no I/O; `InstagramNames`; `platform_names()` / `names_of(key)` for code below integrations), `AccountProfile`, `PostStat`, `PostViews` (views + posted_at; `PostStat` extends it with id/url/`thumbnail_url`), `AccountStats` (`complete` = no cap hit; `.metrics()` = scan totals + `complete`, no windows), `AccountMetrics`, `ViewWindow.of(posts, days, as_of, complete)` (any period derived on read, never stored; `covered`: the scan reached the window start, else its numbers read as unknown, never as a floor).
- `errors.py` — the only exceptions `fetch` raises: `SocialError` (lasting, recorded), `RetryableError` (`reached`, `dead_proxy`), `RateLimitedError` (stops the batch when every try hit it).
- `platforms/base.py` — `Platform(PlatformNames)` ABC: the names plus `proxies()`, `fetch(handle, proxy)`.
- `platforms/instagram.py` — `ofmhelpers.integrations.instagram` client: profile (logged out, via proxies) + newest `OFM_IG_TRACK_MAX_REELS` (96) reels' play counts. Reels: with `cookies` (only the `login` source passes them: the owner's own /cookies upload, never another user's) the logged-in reels-tab query (`InstagramClient.reels_logged_in`, no proxy) when it works, else (and always without cookies) the logged-out reels tab, marked `limited` (UI banner). Private: profile numbers, no posts.

## Instagram hides reels from logged-out visitors (verified 2026-10-20)
- @danywalking: 15 reels in 7 days on Instagram, the logged-out reels tab and timeline both end after 8 (`has_next_page` false), any page size, direct or proxied. @instagram logged out: 96+. So it is per reel (sensitive/age-restricted content), not a page cap; `total_clips_count`/`media_count` give no signal logged out.
- Only a login sees them: the reels-tab GraphQL query (`/graphql/query`, `av` = page `actorID`, `fb_dtsg` from `DTSGInitialData`, same `doc_id`) returned all 15. The REST API (`/api/v1/clips/user/`, `feed/user`, `current_user`) 302s cookie sessions to the home page even when the website is logged in -- don't use it.
- A dead login: its page has `"actorID":null` -> `reels_logged_in` returns None -> logged-out fallback, scan `limited`, banner on /accounts. A user uploading cookies at `/cookies` resyncs their own limited accounts at once (`account_tracker.rescan_limited(user_id)`); the banner is per user (only their accounts are listed).
- `platforms/__init__.py` — `platforms()` registry (lru_cache), `get_platform(key)`.

**New platform (TikTok, Threads, X, Snapchat...)** = its `PlatformNames` class + entry in `schemas/socials.py` `_NAMES`, `platforms/<name>.py` subclass of both (`class XPlatform(XNames, Platform)`) + one entry in `_PLATFORM_TYPES` (`tests/unit/socials/test_socials.py` keeps the two lists in step) (+ its settings group for proxies/limits). Page, filters, add dialog, tracker, DB need no change. Never rename a `key` in use (stored on every account).

Storage (`db/models.py`): `tracked_accounts` (latest `profile`/`metrics` JSONB, `covered_since`, `untracked_at` = "Remove" is a soft untrack: not listed or scanned, every record kept, re-adding the handle resumes the same row; nothing in the app hard-deletes an account, `creator_id`, `notes`), `tracked_posts` (one row per post, unique `(account_id, post_id)`; scans upsert what they read, never delete what they missed; only a successful scan prunes that account's posts older than `post_retention_days` = 2 x longest period, by `posted_at` (failed scans touch nothing: a banned account keeps its data until reachable again); reads return every stored post, no age filter; `covered_since` = earliest publish time the kept posts are complete from: a successful scan whose `AccountStats.reach` (0 when complete, else its oldest post; private = not complete) reaches back to the previous successful scan extends it (`min`), one after a gap (banned/untracked/paused, capped) restarts it at its own reach; never older than the retention cutoff), `platform_account_id` (`AccountProfile.account_id`, IG `pk`; unique per platform): a successful scan whose id another row already holds = a rename -> `_merge_rename` moves snapshots/posts/creator/notes onto the older row, which takes the new handle (untracked cleared), and drops the duplicate; `failed_scans` (consecutive): rescan interval doubles per failure up to `OFM_ACCOUNTS_MAX_RESCAN_INTERVAL_S` (24 h), reset by success/`mark_due`/re-add; by design: a post deleted on the platform counts until it ages out (missing != deleted); expired CDN thumbnails of dead accounts stop loading, numbers stay; a failing account shows its last successful sync's numbers, `account_snapshots` (`followers` column + `metrics` JSONB per successful scan; growth = newest snapshot a full period old; younger accounts show change since the first snapshot, marked partial; one snapshot = no growth), `creators`.
Scheduled scans (the sweep) run on production only (`OFM_ACCOUNTS_SCHEDULED_SCANS` unset; true/false forces it): dev runs on a copy of prod's data and would pay Apify again for the same accounts (owner, 2026-11-07); Sync, Add and a login's first scan work anywhere. Dev's numbers come from a prod snapshot load.
Settings: `AccountsSettings` (`OFM_ACCOUNTS_*`): rescan 6 h, batch 20/job, periods 1(=24h)/7/14/30 d (`OFM_ACCOUNTS_PERIODS_DAYS`, selector order; default 7 via `OFM_ACCOUNTS_DEFAULT_PERIOD_DAYS`, must be listed), top posts 10, page sizes.
