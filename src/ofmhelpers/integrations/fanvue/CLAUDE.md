# Fanvue API

Official docs: https://api.fanvue.com/docs (index https://api.fanvue.com/docs/llms.txt, spec https://api.fanvue.com/docs/openapi-v1.json). Researched 2026-11-05. **Seen on a real agency account (2026-11-05)** where it says so; webhooks have not run against a real delivery yet.

- `client.py` — `FanvueClient(token)`: `me()`, `managed_creators()`, `chats()`, `messages()`, webhook subscriptions. Base `https://api.fanvue.com/v1`, header `X-Fanvue-API-Version: 2025-06-26`. Rate limit 200 requests per 60 s per user per app, 6 at once.
- `oauth.py` — PKCE and tokens. `webhooks.py` — signature and deliveries. `source.py` — `FanvueSource`, this platform's `ChatSource` (`integrations/chat_source.py`). `errors.py`.
- Tokens are kept by `features/chatting/fanvue_tokens.py`, the connect flow is `features/chatting/fanvue_connect.py`; integrations do not touch the database.

## Auth
- **No API keys, no client-credentials grant**: someone must authorise once in a browser. `FANVUE_CLIENT_ID`, `FANVUE_CLIENT_SECRET` in `.env`.
- Authorize `https://auth.fanvue.com/oauth2/auth`, token `https://auth.fanvue.com/oauth2/token`. PKCE S256 mandatory; client auth is HTTP Basic only (body gives `invalid_client`). Scopes: `openid offline_access offline read:self read:chat read:creator`; each must be enabled on the app.
- The redirect URI must be registered exactly in the Developer Area (https://www.fanvue.com/dev): `<APP_BASE_URL>chatting/fanvue/callback`. An unregistered one answers `invalid_request`. An account counts only on the server it was connected on (`chat_accounts.connected_from`): dev runs on a copy of production's database, and a dev sync spending production's refresh token would kill production's authorisation.
- **Refresh tokens are single-use and rotate; reusing one past a short grace window kills the whole authorisation** (`invalid_grant`). So a refresh holds a per-account lock and saves the new pair in the same transaction (`ChatRepository.fresh_token`). A lost answer is presented again at once (`OFM_FANVUE_REFRESH_TRIES`): the docs say waiting breaks the chain (https://api.fanvue.com/docs/authentication/overview.md).
- Seen 2026-11-05: the first refresh of a one-hour-old login answered `invalid_grant`; after reconnecting, two forced refreshes in a row worked. Cause not proven (theory: the app's events or scopes changed in between). The refused reason is logged now.

## Chats
- `GET /v1/chats` (`/v1/creators/{uuid}/chats` for an agency), latest activity first, `size` 1-50, `nextCursor`. `lastMessage`: `uuid`, `sentAt`, `type`, `senderUuid`, `senderRole`.
- `GET /v1/chats/{fanUuid}/messages`, newest first, `limit` 1-50, older pages with the reply's `dateFilter` (`sentBefore`, `receivedBefore`; both null = end). Includes mass messages that reached this fan; the batch endpoint does not.
- **`markAsRead` defaults to true: every call sends `markAsRead=false`**, or monitoring would clear the unread counts chatters work from.
- Seen on the real account: `dateFilter` is `null` on a chat's last page, though the spec shows an object. Unsent mass messages sit in threads (`BROADCAST` + `status: UNSENT`), so `status` must be checked. Some chats answer 400 `Invalid user UUID` on messages; they are not asked again until they change. 1,940 of one creator's 2,003 chats end on a `BROADCAST`, which is why those are not opened unless a fan waits.
- There is no chat id: a chat is a creator and a fan. Stored as `<creator uuid>:<fan uuid>`.
- No block flag exists on a chat, so unlike Stacked a fan who blocked stays counted until answered.

## Webhooks
- `POST /v1/webhooks/subscriptions` `{url, events}` with the creator's token, one destination per call with its own `signingSecret`, returned once. Public HTTPS only: "no redirects, no localhost". No enable flag and no notice when one is disabled after failures, so silence is the only sign (`webhook_quiet_s` handles it).
- Unsigned probe `{"type": "fanvue.webhook.verification"}` first; it must get a 2xx or the destination is not made.
- `X-Fanvue-Signature: t=<s>,v0=<hex>`, HMAC-SHA256 over `<t>.<raw body>`, 300 s tolerance. The docs' samples key it with the secret string as given; to confirm on a real delivery.
- Events used: `creator.message.received`, `.sent`, `.deleted`, `.mass_sent` (scope `read:chat`); `creator.subscription.activated`, `creator.payment.succeeded` (scope `read:creator`). At-least-once, no order promised, id is the top-level `id`. Unknown events must get a 2xx: a 4xx counts toward being disabled.
- **`creator.message.mass_sent` fires once per send, names no recipients, and a mass message never emits `creator.message.sent`.** So it does not answer anyone by itself: it triggers a sync, which opens only chats with a fan waiting and sees whether the broadcast reached them.
- Automated replies do emit `creator.message.sent`, so they count as replies.
- `creator.payment.succeeded` covers paid posts, messages, media, tips and every subscription charge, renewals included: `gross` is what the fan paid in cents, `billing_reason` tells a renewal, `id` is the invoice number. `creator.subscription.activated` is a new or returning subscriber; `price` is not what was charged. Above `OFM_CHATTING_SALE_NOTIFY_CENTS` (5000) a sale gets a pop-up, every subscriber does; kept in `chat_notifications` so nobody being online does not lose one. Every sale, small ones too, is also kept in `chat_sales` (gross cents, since 2026-11-06): the daily report's Fanvue sales (`features/reports/fan_sites.py`), its subscribers from `chat_notifications`.
- `POST /v1/webhooks/test` sends a real signed synthetic event to your own destinations: the way to test without waiting for a fan.
- **Seen 2026-11-05: an agency admin's token gets 403 on `/v1/webhooks/subscriptions` and `/v1/webhooks/test`**, with `read:self read:chat read:creator` granted. So API-made destinations need each creator's own connection; own connection wins over the agency's for that model (`FanvueSource.models`). The `/v1/agencies/*` and creator insights calls answer 403 `Insufficient scopes` without `read:agency`/`read:insights`.

### Events tab (what we use: `FANVUE_EVENT_SECRET`)
Docs: https://api.fanvue.com/docs/webhooks/subscribing.md, https://api.fanvue.com/docs/webhooks/event-catalog.md, https://api.fanvue.com/docs/webhooks/delivery-and-idempotency.md (read 2026-11-05).
- Developer Area -> Events: destinations "for your app as a whole", one per event type, at most 20. **One signing secret per app**, shared by every endpoint ("View signing secret"). `chat_webhooks` still gets one row per model, kept up by every sync round (`cover_models`), so a delivery finds its model's name. A delivery signed with it but for a model not known yet is answered and logged as a warning, never refused: failing answers get a destination disabled.
- An event reaches an endpoint only when "the consenting token holds the topic's scope"; creators who authorised before a scope was added must authorise again. **The docs do not say whether an agency's consent covers its creators: unproven until a real delivery names one.**
- Only a 2xx is a success; a redirect, 4xx, 5xx or timeout is retried with backoff (no schedule given), with no manual replay. A destination that keeps failing is disabled; the app owner is notified in the Developer Area; the toggle in "Events & endpoints" turns it back on; nothing missed while disabled is sent later. The chat sync recovers messages, not subscribers or sales.
- The tab's names: Action purchase paid `app.experience.action.payment.succeeded` (no creator in the payload), New follower `creator.follow.created`, Mass message sent `creator.message.mass_sent`, Message read by fan `creator.message.read_by_fan`, Message received `creator.message.received`, Message sent `creator.message.sent`, Message deleted `creator.message.deleted`, Payment succeeded `creator.payment.succeeded`, Subscription activated `creator.subscription.activated`, Subscription auto-renew changed `creator.subscription.cancel_at_period_end_changed`, Subscription deactivated `creator.subscription.deactivated`, Subscription renewed `creator.subscription.renewed`.
- Every one gets a 2xx; `webhooks.deliveries` acts only on those in `EVENTS` and logs the type of the rest.
- Seen 2026-11-05: a second destination at `/events/fanvue/creator-events` (Outpost/1.0.3), answered 404 38 times with retries at about +1, +3, +7, +15 min. Nothing was lost: its 13 first tries each came in the same minute as a delivery to `/events/fanvue`. A path under `/events/{platform}/` is now heard too; the signature decides. Its body fails `WebhookEnvelope` (2 fields), so it is logged as not understood and answered 200. Likely the deprecated flat events (`eventId`, no `id`/`type`): https://api.fanvue.com/docs/webhooks/event-catalog.md says never subscribe to both, or each occurrence counts twice. Removing that destination in the Events tab is the clean end of it. Seen 19 times 2026-11-05..08 (`fanvue delivery not understood: 2 fields`). Since 2026-11-08 the line names it, values never (fans' words): `... 2 fields (id: missing; type: missing) of type -, keys eventId,message` (`features/chatting/webhooks._named`/`_failed_fields`). Read a day of those lines, then teach `webhooks.py` that shape with a test on the real body.
- A model's emoji reaction answers the fan (owner's decision 2026-11-05). Message reaction `creator.message.reaction` (`sender` creator or fan, `message_uuid`, `created_at`) is the only way to see one: the messages endpoint has no such field (https://api.fanvue.com/docs/creator/messages.md, https://api.fanvue.com/docs/api-reference/get-messages-from-a-chat). So it needs that destination in the Events tab. Removing a reaction emits nothing. A reaction on an older message also answers what the fan wrote before the reaction: the event does not say which is newest.
- Without `creator.message.sent` a reply is only seen by the sync, so a model counts as delivering only when its own reply arrives by webhook (`_shows_replies`), and stays on the 60 s sync otherwise.
